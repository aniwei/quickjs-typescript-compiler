# QuickJS TypeScript Compiler Technical Design

## 1. Overview
This project aims to implement a QuickJS bytecode compiler in TypeScript. The compiler translates TypeScript AST (Abstract Syntax Tree) directly into QuickJS bytecode, mirroring the logic of the original C implementation (`third_party/QuickJS`) to ensure 100% compatibility and behavior.

## 2. Design Principles
1.  **Code Organization**: Class-based structure, following the existing project style.
2.  **Naming Convention**: CamelCase for classes and methods, matching existing style.
3.  **Logic Fidelity**: 100% adherence to `third_party/QuickJS` source code logic.
    *   The parsing phase is skipped (using TypeScript AST).
    *   The code generation phase (AST -> Bytecode) must match the C implementation exactly.
4.  **Module Design**: Modules and functions are translated unit-by-unit from the C source.
5.  **Process Flow**: The compilation flow follows the C source flow.
6.  **Verification**: Functionality is verified using fixture tests, comparing generated bytecode with official QuickJS bytecode.
7.  **Alignment**: Bytecode alignment issues are resolved by analyzing the C source, not by reverse-engineering from tests.
8.  **Environment**: `Env.ts` is immutable. Environment data (atoms, opcodes) is retrieved via `getEnv.ts` from WASM QuickJS.

## 3. Architecture

### 3.1 Core Components

#### `Compiler` (src/compiler/compiler.ts)
The main entry point. It orchestrates the compilation process.
*   **Responsibility**: Traverses the TypeScript AST and invokes code generation methods.
*   **Mapping**: Corresponds to the high-level parsing functions in `parser.c` (e.g., `js_parse_program`, `js_parse_source_element`).

#### `ParseState` (src/compiler/parseState.ts)
Maintains the state of the compilation process.
*   **Responsibility**: Holds the current token (simulated from AST), current function definition, context, and other parsing state.
*   **Mapping**: Corresponds to `JSParseState` struct in `parser.c`.

#### `JSFunctionDef` (src/compiler/jsFunctionDef.ts)
Represents a function being compiled.
*   **Responsibility**: Manages bytecode buffer, constants, variables, scopes, and labels for a specific function.
*   **Mapping**: Corresponds to `JSFunctionDef` struct in `quickjs.c` / `function.c`.

#### `BytecodeWriter` (src/bytecode/bytecodeWriter.ts)
Handles the low-level writing of bytecode instructions.
*   **Responsibility**: Writes opcodes and operands to the buffer. Handles endianness and variable-length encoding.
*   **Mapping**: Corresponds to `emit_op`, `emit_u32`, etc., in `parser.c`.

#### `ScopeManager` (src/compiler/scopeManager.ts)
Manages variable scopes and resolution.
*   **Responsibility**: Tracks variable declarations, block scopes, and resolves identifiers to stack indices or environment variables.
*   **Mapping**: Logic scattered in `parser.c` related to `push_scope`, `pop_scope`, `add_var`, etc.

#### `LabelManager` (src/compiler/labelManager.ts)
Manages control flow labels (break, continue, goto).
*   **Responsibility**: Tracks label targets and resolves jumps.
*   **Mapping**: Logic related to `push_label`, `pop_label`, `emit_goto`, etc.

### 3.2 Data Structures

*   **`Token`**: Represents a source token. In this implementation, it's derived from AST nodes.
*   **`Atom`**: Represents a unique string identifier, managed via `Env.ts`.
*   **`Opcode`**: Enumeration of QuickJS opcodes.

## 4. Translation Strategy

### 4.1 AST Traversal vs. Parsing
The original QuickJS compiler is a single-pass parser + compiler. It reads tokens and emits bytecode.
Our implementation uses TypeScript AST.
*   **Mapping**:
    *   `next_token()` in C -> Moving to the next node in AST traversal.
    *   `js_parse_statement()` -> `visitStatement(node: ts.Statement)`.
    *   `js_parse_expr()` -> `visitExpression(node: ts.Expression)`.

### 4.2 Function-by-Function Translation
We will identify key functions in `parser.c` and translate them into methods in `Compiler` or `JSFunctionDef`.

| C Function (parser.c) | TypeScript Method | Description |
| :--- | :--- | :--- |
| `js_create_function` | `JSFunctionDef.create` | Initialize a new function definition. |
| `emit_op` | `BytecodeWriter.emitOp` | Write an opcode. |
| `js_parse_program` | `Compiler.compileProgram` | Entry point for program compilation. |
| `js_parse_function_body` | `Compiler.compileFunctionBody` | Compile function body. |
| `js_parse_statement` | `Compiler.compileStatement` | Compile a single statement. |
| `js_parse_expr` | `Compiler.compileExpression` | Compile an expression. |

### 4.3 Bytecode Alignment
To ensure byte-perfect output:
1.  **Opcode Values**: Must match `quickjs-opcode.h` (via `Env.ts`).
2.  **Operand Encoding**: Must match `emit_u32`, `emit_short`, etc.
3.  **Constant Pool**: Constants must be added in the exact same order.
4.  **Scope & Stack**: Variable indices and stack depth must be tracked exactly as in C.

## 5. Development Workflow
1.  **Analyze**: Read the C function in `parser.c`.
2.  **Translate**: Implement the equivalent TypeScript method.
3.  **Test**: Run fixture tests (`pnpm test`) to verify bytecode generation.
4.  **Debug**: If bytecode differs, use `disasm` and debug logs to compare with C output.
